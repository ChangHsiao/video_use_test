# 開發工作流

與 Agent 協作開發的流程。目前在試用階段，每次做完一個修改，都在第 7 步檢討並調整這份文件。

## 七個步驟

| 步驟 | 誰做什麼 | 產出 | 進入下一步的條件 |
|---|---|---|---|
| 1. 釐清 | 使用者說要做什麼；Agent 提問、提出做法和取捨 | `specs/` 裡的規格文件 | 使用者同意規格 |
| 2. 計畫 | Agent 寫出要改哪些檔案、怎麼驗證 | `plans/` 裡的計畫文件 | 使用者看懂步驟清單並同意 |
| 3. 開分支 | Agent 提供指令，使用者自己開 branch | 新的 branch | 不在 `main` 上直接修改 |
| 4. 實作 | Agent 照計畫小步修改，每一步說明改了什麼 | 程式碼修改 | 使用者看過 diff |
| 5. 驗證 | Agent 實際執行，對照規格的「怎樣算完成」 | 執行結果 | 真的跑過，不是「應該可以」 |
| 6. 提交 | Agent 提供指令，使用者自己 commit、push | commit | 文件和程式碼放在同一個 commit |
| 7. 回顧 | 一起整理 | 更新 `decisions.md`、學習筆記、這份工作流 | — |

**小修改**（只改一兩行、不影響程式行為，例如修錯字）可以跳過第 1、2 步，但第 3、6 步照做。

## 文件規則

### 三種文件

| 文件 | 位置 | 數量 | 寫完之後 |
|---|---|---|---|
| 規格（要做什麼、為什麼） | `specs/YYYY-MM-DD-主題.md` | 每個修改一份 | 決定改變時要更新 |
| 計畫（怎麼做） | `plans/YYYY-MM-DD-主題.md` | 每個修改一份 | 完成後不用維護 |
| 決策紀錄 | `decisions.md` | 整個專案一份 | 只新增，不修改舊的紀錄 |

**決策紀錄的收錄標準**：看到專案現在的樣子，未來的自己或 Agent 會不會問「為什麼是這樣？」會的話才記。環境設定寫在 `CLAUDE.md`，工作方式和偏好寫在這份文件。

範本在 `specs/_template.md` 和 `plans/_template.md`。

### 兩層寫法
規格和計畫都分成兩層：

- **給使用者看的**：白話、10 行以內，專有名詞第一次出現時附上全名和一句說明。使用者一定要讀懂這一層才能同意
- **給 Agent 看的**：精確、完整，可以有程式細節和專有名詞

### Agent 的規則
- 實作時如果需要偏離計畫，先停下來說明原因，等使用者同意
- 不替使用者執行 `git add` / `git commit` / `git push` / 開 branch，只提供指令和說明
- 做出符合收錄標準的決定時，提醒使用者記進 `decisions.md`
